# TASK-021: сборка канона НД в Word из базы и изменений (исследование)

Уровень риска: **low** (всё в `poc/canon_assembly/`, репозиторий НД только читается). Перенос в `scripts/` — отдельный план уровня medium, когда метод даст ≥98 %.

## Контекст
- Канон документа БНД — PDF-эталон (листы замены вшиты), Word обновляется редко; изменения лежат рядом: «Лист изменения» (протокол правок: где → что → на что) и «Листы замены» (новый текст листов).
- Исследование 28–29.09 в Claude Code (прототипы в scratchpad, перенос — шаг 1): содержательный текст (от «Общих положений» до приложений) собирается на 94 % (КД-РГ-174-05) и 79 % (РД-М1.029-07); остатки — строки протокола, которые не применены, и неверная привязка листов замены по похожести.
- Решение human 29.09: применять протокол правок как «протокол разногласий», листы замены — источник нового текста, где его нет в протоколе; эталон — проверка. Считать только содержательный текст, служебные разделы 1–4 и колонтитулы — отдельно.
- Пилоты: `data/bnd_corpus/documents/СУБП/M1/РД-М1.029-07`, `data/bnd_corpus/documents/СМК/_unclassified/КД-РГ-174-05` (по 5 изменений, цепочки без пропусков).

## Цель (уточнена human 29–30.09.2026)
Не «Word на 100 %», а **структурированная запись документа** для typed extraction и графа: пункты с проверенным текстом и источником каждого абзаца (Word / протокол / лист замены / PDF), история изменений по пунктам (из протоколов), реквизиты, таблицы и рисунки из Word, список GAP.
- Объём: **358 документов БНД** с эталоном PDF в текущей выгрузке (169 без изменений + 189 с изменениями). РПП не нужны. РОТО (КД-РД-В6.025-03) — после докачки эталона (внешняя ссылка). РПП-2017-02 исключён.
- **Контент** = текст документа без колонтитулов, штампов «Изменение №», листа регистрации изменений и титульного листа (с титула — только наименование, берётся из каталога). Служебные разделы (предисловие, перечень рассылки, содержание) — отдельный блок метаданных, в проверку полноты контента не входят.
- OCR для БНД не нужен (сканированных действующих эталонов нет; сканы — только титул и лист регистрации, которые вне контента).
- Приёмка: полнота текста по страницам эталона (≥98 %, остаток — с классом причины), учёт каждой страницы, цепочка изменений 1…N (пустые карточки Lotus — GAP), связность нумерации пунктов, выборочный Gold Standard.
- Графика: фигуры/надписи Word и VML — текст из XML; встроенный Visio — фигуры и связи; Excel — таблица; картинки — отсев логотипов/подписей, схемы — VLM с пометкой «распознано, требует проверки»; исходный файл рисунка — в записи.
- Проверить Docling (DOCX и PDF) как основу формата записи (DoclingDocument, D-008) до решения.

## Шаг 6 (решение human 30.09): реинжиниринг Word до соответствия эталону PDF
Цель: Word-канон (SSOT в машиночитаемом виде) + режим «исправленная (markup) / чистая (clean)» для раздачи разработчикам. Главное — итоговый текст эталона; расхождения протокол↔лист — второстепенны.
- Сборка по страницам, детерминированно: страницы эталона без штампа = база (якоря по их первым/последним строкам); подряд идущие страницы со штампами вырезаются из базы и заменяются разделами последних листов замены с теми же номерами (`pagediff.py`: метки из колонтитулов, поле PAGE → `pgNumType start`, перенос без разрыва — по перечню страниц протокола).
- Word 2013 (COM через powershell.exe, копии во временной папке Windows): `.doc`→`.docx`, вставка разделов листов (`InsertFile`) с оформлением, `Compare` база↔канон = markup, номера автонумерации (`ListFormat.ListString`).
- Проверка: каждая строка эталона (контент) есть в каноне; текст канона, которого нет в эталоне; нумерация пунктов канона = эталон; стыки страниц.
- Тест: КД-РД-В5.058-04, РГ-184-06, КД-РД-Б1.041-04, КД-ДП-Б1.011-04, ДП-Б1.024-06. Результат и журнал дефектов — `poc/canon_assembly/reeng/`.

## Шаги
1. **coder** — перенос прототипов (`assemble.py`, `body.py`, `protocol.py`) в `poc/canon_assembly/` без изменения логики.
   → verify: `python3 poc/canon_assembly/body.py <пилот> --guard` даёт те же цифры (174: 93.8 %, 029: 79.4 %).
2. **coder** — `poc/canon_assembly/docx_numbering.py`: номера автонумерации абзацев Word (`numbering.xml`: `abstractNum`/`num`/`lvlOverride`, `ilvl`, `lvlText` вида `%1.%2.`, `start`, `numFmt` decimal/буквы/римские, сброс нижних уровней, стиль с `numPr`).
   → verify: на базовых Word двух пилотов доля заголовков/пунктов, чей вычисленный номер встречается в тексте эталона PDF рядом с тем же текстом, ≥95 %; список несовпадений.
3. **extractor** — протоколы 10 листов изменения → `poc/canon_assembly/ops/<документ>/izm<N>.json` по схеме ниже, у каждой правки — дословная строка-источник.
   → verify (orchestrator): выборочно 20 правок против текста листа; ни одной правки без `source_line`.
4. **orchestrator + coder** — применение правок по адресам пунктов, листы замены — где `new_in_sheets`, сверка содержательного текста с эталоном.
   → verify: ≥98 % на пилотах; каждое оставшееся расхождение — с объяснением (GAP / отменено следующим изменением / скан / вёрстка).

## Схема правки (шаг 3)
```json
{"doc": "КД-РГ-174-05", "izm": 1, "sheets_line": "Изменение внести заменой листов (…)",
 "ops": [{"n": 1, "source_line": "дословно из листа",
   "locator": {"section": "7", "point": "7.2.5", "part": "абзац/дефис/строка таблицы/приложение — как в тексте", "raw": "дословное указание места"},
   "action": "replace | restate | insert | delete | renumber | other",
   "old": "заменяемый/исключаемый текст или null",
   "new": "новый текст или null",
   "new_in_sheets": true}]}
```
`new_in_sheets: true` — протокол не приводит новый текст («изложить в новой редакции» без текста, «таблицу изложить…»). Ничего не дописывать от себя (Rule 0): неясное место — `locator.raw` и `action: other`.

## Risks
- Автонумерация Word сложна (стили, переопределения, продолжение списков) — поэтому проверка по эталону, а не «на глаз».
- LLM-разбор протокола может исказить текст правки — поэтому дословный `source_line` и выборочная сверка.

## Правила готовности и изоляции (решение human 05.10.2026, без пересмотра в процессе)
1. **Готов** (`ready`): все строки контента эталона найдены в каноне, номера пунктов совпадают, повторов нет (verify_canon: missing = numbered_bad = duplicates = frozen = 0). **Годен по сути** (`ready_core`): пункты разделов 6+ совпадают на 100 %, нет ненайденных строк A/B/U и неверных номеров в 6+, приложения — только по числу. Для обоих обязательно: файл открывается в Word (wordopen_check) — для py-сборки.
2. **Принят** (`accepted` в live/state.json): готов или годен по сути + прошёл открытие в Word. Принятый документ новым кодом не пересобирается и в регрессию не входит. Пересборка — только если документ изменился в Lotus (ночная обработка), тогда он заново проходит п. 1.
3. Правки кода касаются только непринятых. Круг = пересборка непринятых + перенос в live только улучшений (`nightly_canon.py --adopt`). Тест кода — постоянный набор 26 документов (stepA/regress_set.txt), а не пересборка канона.
4. Конец хардкода — по факту: документ, не сдвинувшийся два круга подряд, уходит в «остаток» (корпоративная модель / ручное решение); хардкод завершается, когда круг даёт < 5 новых принятых.
