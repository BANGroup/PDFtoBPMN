# 04. Справочники для наполнения графа

Машиночитаемая версия — [catalogs/catalogs.yaml](catalogs/catalogs.yaml). Решение — D-045.

## 1. Принципы

1. **Минимум — только то, без чего не собрать каркас графа** (D-044). Остальные справочники — по мере надобности.
2. **Поля проектируются от Business Studio.** Сначала поля BS (справка BS, КД-СТ-161 приложения 2–3), затем наши дополнения — отдельной колонкой. Дополнения в BS заводятся пользовательскими параметрами через MetaEdit (КД-СТ-161 п. 9.2).
3. **Связи между справочниками — по идентификаторам**, не по тексту названий.
4. **Rule 0 действует и для справочников:** пустое поле остаётся пустым и видно как пробел; значения не подставляются по аналогии.

## 2. Минимальный набор

| # | Справочник | BS | Зачем графу | Обязательные поля (предварительно) |
|---|---|---|---|---|
| 1 | Процессы (дерево и коды) | Деятельность | Привязка схемы к процессу; переходы между схемами (LINK) | код, название, родитель, владелец |
| 2 | Оргструктура | Оргединицы | Дорожка-подразделение обязательна; должность → подразделение | подразделение: id, название, родитель; должность: id, название, подразделение |
| 3 | Документы | Документы (НСД) | Источник (evidence) каждого элемента; ссылки между документами | код, название, тип, процесс, подразделение-владелец, статус |
| 4 | Термины и сокращения | Термины | Не узлы графа; склейка, подсказка типа, связи между документами | название, определение, документ-источник, вид, статус |

Позже, когда понадобятся: программные продукты, базы данных, внешние участники, показатели, риски.

Поля справочников 1–3 проектируются следующим шагом; здесь зафиксирован только состав и предварительный минимум.

## 3. Роль терминов в машинной сборке графа

Термины в граф не входят, но сборщик графа опирается на них:

1. **Склейка: одно понятие — один узел.** «ВС» / «воздушное судно», «КН» / «карта-наряд», «ОТК» / «отдел технического контроля». Без словаря — несколько узлов вместо одного, связи между процессами через общие документы и подразделения не сходятся. Главная роль.
2. **Подсказка типа узла.** Определение часто прямо называет класс: «… — документ» → объект-документ; «… — информационная система» → программный продукт; «… — должностное лицо» → оргединица. Тип берётся из определения с цитатой; не назван — не ставится.
3. **Связи и дефекты между документами.** Термин определён в документе А и используется в Б → Б зависит от А (скрытая связь вне «Нормативных ссылок»). Разные определения одного термина → `≠ контекст`. Используется, но нигде не определён → `⚠ GAP`.

Это же — основа ИИ-нормоконтроля «применение определений и сокращений + детекция новых» (`docs/concept_perspective.md`, направление 4).

### Поля справочника терминов

| Поле | BS | Обязательно | Назначение |
|---|---|---|---|
| Название (термин или сокращение) | Название | да | ключ |
| Определение / расшифровка | Описание | да | смысл, подсказка типа |
| Документ, где определён | бинарная связь «определяется» (НД → термин) | да | источник, связь между документами |
| Вид: термин / сокращение | — (правило написания: сокращение прописными) | да | — |
| Полная форма | — (в BS — в «Описании») | для сокращений | склейка |
| Варианты написания, синонимы | — | нет | склейка |
| Тип узла графа | — | нет; только если назван в определении | подсказка экстрактору |
| Статус: черновой / утверждён | — | да | утверждает только человек |

## 5. Порядок работы

1. **Процессы** — на них ссылаются все остальные; один справочник вместо трёх версий, источник — РК01-2026-08.
2. **Оргструктура** — слой должностей с id и привязкой к подразделению.
3. **Документы** — связь с процессами и оргструктурой по id; разбор пропусков подразделения-владельца.
4. **Термины** — чистка дублей, статус утверждения.

На каждом шаге: поля BS → наши дополнения → источник наполнения → сверка с имеющимися данными → пробелы.
