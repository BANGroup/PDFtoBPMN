# 01. Концепция: минимальная модель графа процессов

Машиночитаемая версия — [schema/process_graph.schema.yaml](schema/process_graph.schema.yaml) и [rules/connectivity.yaml](rules/connectivity.yaml).

## 1. Принципы

1. **Опора — практика.** Основа модели — реальные схемы и методики практиков (Репин, Исаев) и то, как данные хранит Business Studio. КД-СТ-161 — сверка, не догма: компания ещё учится моделированию.
2. **Каркас и опции.** Обязательное — то, без чего схема не собирается. Опциональное пишется, только если есть в тексте.
3. **Связность — главное требование каркаса.** Схема не должна иметь подвешенных элементов: из начала всегда есть путь в конец или в переход на другую схему. Важно **наличие** перемычек, а не их наполнение (подписи, условия).
4. **Rule 0: вакуум не заполняется.** Если в тексте нет элемента или связи — их нет в графе. Схема остаётся с подвешенными частями и предупреждениями. ИИ строго пишет как есть и не додумывает.
5. **Доказательство у всего.** Каждый узел, ребро и атрибут несёт ссылку на документ, пункт и цитату. Без цитаты элемент не существует.
6. **Имя — как в тексте.** Нормализованное имя хранится отдельно, оригинал не затирается.
7. **Неизвестное — это значение.** Тип шлюза, задачи, события по умолчанию — «не определён», а не угаданный.

## 2. Как получено значение (evidence.mode)

| Режим | Значение | Пример |
|---|---|---|
| `explicit` | прямо сказано в тексте | «Юрист согласует проект договора» |
| `structural` | следует из структуры документа: нумерованный порядок шагов в разделе-процедуре, строка таблицы «шаг — исполнитель — срок», схема в документе | шаг 3 таблицы идёт после шага 2 |
| `reference` | взято из справочника (оргструктура, реестр документов), а не из текста | подразделение юриста — из штатного расписания |

Режима «догадка» нет. Нумерация пунктов в описательных разделах **не** считается порядком шагов (`structural` — только для разделов-процедур и таблиц шагов).

## 3. Каркас — обязательные элементы

| Элемент | Business Studio | BPMN | Обязательные атрибуты |
|---|---|---|---|
| Процесс | Процесс / единица деятельности | process, pool | название, evidence |
| Задача | Задача (процесс без декомпозиции) | task | название как в тексте, evidence |
| Стартовое событие | Стартовое событие | startEvent | название |
| Конечное событие | Конечное событие | endEvent | название |
| Переход на другую схему | Ссылка / свёрнутый пул / процесс-ссылка | linkEvent, messageFlow → pool, callActivity | на что ссылается (как в тексте) |
| Шлюз — **если в тексте есть ветвление** | Шлюз | gateway | тип (включая «не определён») |
| Подразделение-исполнитель | Оргединица (подразделение) — дорожка | lane | название |

### Переход на другую схему — три вида
- **событие-ссылка** (Link, кружок со стрелкой) — продолжение того же процесса на другом листе;
- **событие-сообщение + поток сообщений к свёрнутому пулу** другого процесса (так в КД-СТ-161: предыдущий/следующий процесс);
- **процесс-ссылка** (Call Activity, типовой процесс) — вызов другой схемы как блока.

У Исаева тот же смысл несут подписи «Вход из предыдущей процедуры …», «Переход к процедуре …».

### Исполнитель
- **Подразделение обязательно** — это дорожка.
- Должность, роль, группа, человек — **опционально**, уровень ниже (вложенная дорожка / уточнение).
- Названа только должность → подразделение берётся из справочника оргструктуры (`reference`), если должность там однозначна. Нет в справочнике или неоднозначна → предупреждение, подразделение не выбирается наугад.
- Собирательный исполнитель («согласующие подразделения», «члены комиссии») сохраняется как есть на нижнем уровне; состав — только если перечислен в тексте.

## 4. Каркас — обязательные рёбра-перемычки

| Ребро | Business Studio | BPMN | Где обязательно |
|---|---|---|---|
| Поток управления | Поток управления | sequenceFlow | старт → блок; блок → блок; блок ↔ шлюз; шлюз → шлюз; блок → конец; блок → переход |
| Выполняет | тип связи «выполняет» | задача в дорожке | подразделение → каждая задача |
| Декомпозиция | дочерний процесс | вложенность | процесс → его задачи (ставится по разделу документа, `structural`) |

Подпись и условие потока **не обязательны**. Обязательно само наличие перемычки.

## 5. Правила связности (проверяет валидатор)

| Правило | Проверка |
|---|---|
| C1 | Есть хотя бы одно стартовое событие |
| C2 | Есть хотя бы одно конечное событие или переход на другую схему |
| C3 | Каждый элемент достижим из старта |
| C4 | Из каждого элемента достижим конец или переход |
| C5 | Нет висящих: у каждого, кроме старта, есть входящий поток; у каждого, кроме конца и перехода, — исходящий |
| C6 | Шлюз ветвления: ≥ 2 исходящих; шлюз слияния: ≥ 2 входящих |
| C7 | У каждой задачи есть подразделение-исполнитель |

Нарушение **не блокирует** сохранение схемы: элемент остаётся висеть, в протокол пишется GAP с номером правила и пунктом документа. Валидатор ничего не дорисовывает.

## 6. Опциональные элементы

| Элемент | Business Studio | Когда создаётся |
|---|---|---|
| Промежуточное событие | Промежуточное событие | таймер / сообщение / условие названы прямо |
| Документ (корпуса или внешний НД) | Документы / Нормативно-справочные документы | на него есть ссылка в тексте; документ-источник — всегда |
| Объект: документ / информация / материальный объект | Функциональные объекты | шаг получает или формирует его |
| База данных | Базы данных | названо хранилище, архив, база |
| Программный продукт | Программные продукты | «в системе X» |
| Внешняя ссылка | Внешние ссылки (свёрнутый пул) | клиент, поставщик, надзор, другая компания |
| Бизнес-правило | — (сноска) | норма-условие, не являющаяся шагом |
| Риск | — (у практиков есть) | риск назван в тексте |
| Показатель | Показатели | **только если контроль измеримый**: порог, целевое значение, единица или формула |

## 7. Опциональные рёбра

| Ребро | Business Studio | Откуда → куда |
|---|---|---|
| Владелец ⚑ | субъект процесса «владелец» | подразделение → процесс |
| Участник | субъект процесса «участник» | оргединица → задача / процесс (роль: согласует, утверждает, информируется, контролирует) |
| Вход | «предоставляет входные данные для», «является входом для», «используется» | объект → задача (+ статус документа) |
| Выход | «имеет на выходе», «создаёт на выходе», «изменяет» | задача → объект (+ статус документа) |
| Хранится в | ассоциация с базой данных | объект → база данных / программный продукт |
| Поддерживает / выполняет | «поддерживает», «выполняет» | программный продукт → задача |
| Поток сообщений ⚑ | Поток сообщений | задача / событие → переход / внешняя ссылка (+ передаваемый объект) |
| Нормативно-справочный документ | список «Нормативно-справочные документы» | процесс → документ (свой источник — автоматически) |
| Входит в подразделение | иерархия оргструктуры | должность → подразделение |
| Состав роли / группы | «Назначение на роль», агрегация | оргединица → роль / группа |
| Подчинение | «Административное» / «Функциональное подчинение» | из справочника, не из текста |
| Правило для | — | бизнес-правило → шлюз / задача |
| Риск | — | риск → задача / процесс |
| Снижает риск | — | контрольная задача → риск |
| Измеряется показателем | — | контрольная задача → показатель |
| Измеряет | — | показатель → процесс |
| Ответственный за показатель | «ответственный за выполнение» | оргединица → показатель |
| Часть ИС | тип ПП: ИС → модуль → функция | программный продукт → программный продукт |

⚑ — отсутствие даёт мягкое предупреждение (процесс без владельца, изолированный процесс).

## 8. Принятые решения и причины

| # | Решение | Причина |
|---|---|---|
| Р1 | Обязательны: процесс, задача, старт, конец, переход, шлюз (если есть ветвление), подразделение | Без них схема не собирается; так у всех практиков и в BS |
| Р2 | Обязательные рёбра — перемычки потока управления + «выполняет» + декомпозиция; важно наличие, не наполнение | Требование связности: путь из начала в конец или переход |
| Р3 | Подразделение обязательно, ниже — опционально | Дорожка = подразделение; должность/роль/группа/человек — уточнение |
| Р4 | Нормативный документ = узел «Документ»; документ-источник автоматически регулирует свой процесс | Иначе дубль: источник шага и НСД процесса — один и тот же документ |
| Р5 | Контроль — признак задачи, а не отдельный узел | У Репина контрольная точка — операция; в тексте СМК контроль записан как шаг |
| Р6 | Показатель — только для измеримого контроля | KPI без меры — не показатель; меру ИИ не выводит |
| Р7 | Термины — отдельный словарь, не узлы графа | Схеме процесса не нужны; нужны для нормализации имён и RAG |
| Р8 | Риски — опция | У практиков есть, в КД-СТ-161 нет |
| Р9 | Статус документа — атрибут ребра вход/выход | Оба практика показывают один документ в разных состояниях |
| Р10 | База данных отдельно от программного продукта, связь «хранится в» | Так в BS и у Репина; одна система может быть и ПО, и хранилищем |
| Р11 | Явные связи между процессами (переход, поток сообщений) — в дополнение к связям через общие объекты | У Исаева и в КД-СТ-161 они нарисованы явно |
| Р12 | Имена типов — английские идентификаторы в коде, русская подпись BS у каждого | Выгрузка в BS без перевода, аналитику — знакомые слова |
| Р13 | Цели (BSC) не входят | К схеме процесса не нужны |

## 9. Чего ИИ не делает

- Не дорисовывает возврат на доработку, если в тексте нет «вернуть», «повторно», «на доработку».
- Не выбирает между параллельным и исключающим шлюзом при двусмысленной формулировке — пишет «не определён».
- Не назначает исполнителя по смыслу.
- Не делает документ входом или выходом, если не сказано, что шаг его получает или формирует.
- Не добавляет конец, переход или шлюз «для замыкания» схемы.
- Не превращает раздел «Ответственность» и перечни форм/систем в последовательность задач (антипаттерны Rule 0).
- Не выводит порог или формулу показателя из общего смысла.
